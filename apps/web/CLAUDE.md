# apps/web

Next.js 16.3.1 frontend, App Router, TypeScript, React 19. Scripts: `package.json` here; the root `package.json` wraps them as `<script>:web`.

Why anything here is the way it is: [`HISTORY.md`](HISTORY.md) (repo-wide changes: [root `HISTORY.md`](../../HISTORY.md)). Per-module architecture and function references: `docs/modules/INDEX.md` (`module-web-*`) — one doc at a time, and updated in the same change as the module, per the root `CLAUDE.md`'s Module documentation section. The `@AGENTS.md` block above asks for the Next.js guides: they live under the **root** `node_modules/next/dist/docs/` (`next` is hoisted there, not into `apps/web/node_modules`), and one guide — for the API you touch — is what to read, not the folder.

## Structure — what the code doesn't say

- `src/app/` is the App Router tree: `page.tsx` (the auth-gated dashboard), `register/`, `login/`, `profile/`, `meetings/[id]/`, `actions/*.ts` (the Server Actions behind those pages) and `api/**/route.ts` — same-origin proxies that carry file and avatar bytes so the session token never reaches the browser. `icon.tsx` generates the favicon at request time via `next/og`'s `ImageResponse`, replacing the default `favicon.ico`.
- `src/lib/` holds the server-only fetch clients for `apps/api` (`*-api.ts`), the `httpOnly` session cookie (`session.ts`), the allow-listed proxy forwarder (`api-proxy.ts`) and the browser-side limits (`*-limits.ts`, hand-duplicated from `apps/api` — see Conventions). Path alias `@/*` → `src/*`.
- `src/components/` — Client Components, kebab-case, grouped by feature (`files/`, `profile/`, `icons/`).
- Tests: unit (`*.spec.ts(x)`) and integration (`*.int-spec.ts(x)`) specs are colocated under `src/` and run on Vitest (`vitest.config.mts`, `vitest.setup.ts`, the `server-only` stand-in in `test/stubs/`); Playwright specs live in `e2e/` and start only this app's dev server (`playwright.config.ts`) — `apps/api` and Postgres must already be up, the API via `dev:api:e2e` (root `CLAUDE.md`, Testing).
- Own ESLint config (`eslint-config-next`) — the root `CLAUDE.md`'s Layout section says why it can't merge with `apps/api`'s.

## Conventions

- JSDoc required for all functions — see root `CLAUDE.md`.
- No shared types package with `apps/api` yet — request/response shapes and limits (`RegisterInput`/`AuthResponse` in `src/lib/auth-api.ts`, `MAX_FILE_BYTES` in `src/lib/file-limits.ts`) are hand-duplicated from the backend, JSDoc-marked as such, and changed in the same commit as the original (root `CLAUDE.md`, Dependencies).
- `apps/api` is called server-to-server from Server Actions and Route Handlers, at `API_BASE_URL` from the monorepo-root `.env` — this app has no `.env` of its own; `next.config.ts` loads the root one via `@next/env`. CORS on the backend stays in place for any future browser-side call.
- UI components come from [HeroUI v3](https://heroui.com/docs/react) (`@heroui/react`), styled via Tailwind CSS v4 (`@heroui/styles` imported after `tailwindcss` in `src/app/globals.css`). No `HeroUIProvider` — v3 doesn't need one. Use HeroUI's compound components (`Card.Header`, `Card.Title`, …) rather than flattening to props, and `onPress` instead of `onClick`; the `heroui-react` skill, when loaded, has the component docs. Theme is fixed to `light` (`className="light" data-theme="light"` on `<html>` in `layout.tsx`) — no theme switching wired up yet.
- **No flash of wrong auth/session state**: any user/session state that affects the initial render (signed-in/signed-out, theme and anything derived from it) is read and applied _before_ the page renders, never client-side after mount — reading it in a `useEffect`/`useSyncExternalStore` against `localStorage` produces a visible flicker or layout shift as the UI flips once JS runs. In practice the JWT lives in an `httpOnly` cookie a Server Component can read (`getSession()`), so the initial HTML already reflects sign-in state — see `docs/modules/module-web-auth.md`.
- **Auth-gated routes redirect server-side, before render**: a protected page checks `getSession()` first thing in its Server Component and calls `redirect('/login')` before producing any JSX when there is no session — or when the first `apps/api` call answers `401`, which means the session is gone. Never a client-side "redirecting…" state or a gate in `useEffect`.

## Development workflow

- **Performance and bundle size**: before writing or reviewing React/Next.js code, consult the `vercel-react-best-practices` skill when it is loaded; otherwise follow the Next.js docs directly. Either way: Server Components, Server Actions and the current Next.js data-fetching/mutation APIs by default; a Client Component only when the page genuinely needs interactivity, local state or a browser API (`/register`/`/login` are Client Components for their per-keystroke validation, but submit through a Server Action, not a local `fetch`).
- **Caching and Redis**: any server-side caching added here (Route Handlers, Server Actions, `fetch`/`unstable_cache`, …) treats Redis as optional/best-effort per the root `CLAUDE.md`'s Redis convention — degrade to the uncached path, never fail the request. Short TTLs (minutes, not hours); when a mutation changes cached state, invalidate the specific keys it affects immediately rather than waiting on TTL or flushing everything.
- **UI review**: after building or changing UI, review it with the `web-design-guidelines` skill, then the `ui-ux-pro-max` skill (its findings win where they conflict) — when they are loaded; otherwise review by hand against the conventions above. Verify visually against a running dev server rather than from source alone: the Playwright MCP tools (navigate, snapshot, screenshot) when present, else per the root `CLAUDE.md`'s Optional tooling section.
- **Refactoring**: only what the root `CLAUDE.md`'s Size and Refactoring rules or an explicit request demand — never speculatively because a change is passing through the area. Before starting: run the full check (`lint`, `test`, `test:e2e`) and confirm it is green, then capture the current visual state of every affected page (screenshots under `screenshots/`) as a baseline. Refactor in small steps; after each, re-run lint/tests and re-screenshot the same pages to confirm nothing moved before taking the next.

## Testing

Three tiers, test-first and outside in, per the root `CLAUDE.md`'s Testing section. Playwright owns `e2e/`; **unit and integration run on Vitest + React Testing Library** and are written first, in the inner loop, against the units the e2e scenario needs.

- **Unit** — `src/**/*.spec.ts(x)`, colocated. Pure logic in `src/lib` (`file-limits.ts`, `file-preview.ts`, `meetings-api.ts`'s upcoming/past split, `session.ts`'s claim decoding) and **Client Components** through RTL, driven with `@testing-library/user-event` and queried by role/label rather than by class or test id. HeroUI's `onPress` responds to `userEvent.click` in jsdom — `src/components/files/file-preview.spec.tsx` is the worked example.
- **Integration** — `src/**/*.int-spec.ts(x)`, colocated. **Route Handlers and Server Actions called directly**: import the exported `GET`/`POST` (or the action), hand it a real `Request` and Next's `params` Promise, mock `next/headers` with `vi.mock` and `fetch` with `vi.stubGlobal`, then assert on what reached the upstream and what came back. This is the tier that pins the security-critical seams the browser can't see into — the proxy's request/response header allow-list, the bearer token attached server-side while the caller's own `Authorization` is dropped, the pre-upstream `401`. `src/app/api/meetings/[meetingId]/files/[fileId]/content/route.int-spec.ts` is the worked example.
- **E2E** — `e2e/*.spec.ts` (Playwright). Pages, navigation, redirects, the real API, and everything that only exists in a browser. Needs Postgres and `apps/api` up via `dev:api:e2e` — the root `CLAUDE.md`'s Testing section says why the headroom is required.

**Async Server Components cannot be rendered by Vitest/RTL** — a React-level limitation Next's own Vitest guide states outright (`node_modules/next/dist/docs/01-app/02-guides/testing/vitest.md` at the repo root). Don't fight it with mocks: a page's rendering, its auth gate and its data fetching are e2e's job. What a Server Component delegates to — the `src/lib` function, the Client Component, the Server Action — is exactly what the two lower tiers cover, so pushing logic out of the component into those places is what makes it testable.

Mechanics worth knowing before writing a spec: the default environment is **jsdom**, and a spec that needs real Node globals (`Request`/`Response`/`fetch`, `Buffer`) opts out per file with a `// @vitest-environment node` docblock on its first line; `describe`/`it`/`expect`/`vi` are **imported explicitly** from `vitest` (no `globals: true`); `@testing-library/jest-dom`'s matchers and RTL's between-test cleanup are wired in `vitest.setup.ts`; `server-only` is aliased to an inert stub (`test/stubs/server-only.ts`) because the real package throws unless the resolver applies React's `react-server` condition, which Vitest can't without swapping React for its server build; Vitest only looks under `src/`, so `e2e/` is never picked up by `test`, and vice versa.

**Security test cases are mandatory, not optional**, and each belongs at the lowest tier that can prove it: the proxy routes' header allow-list, unauthenticated refusal before any upstream call, and id escaping as integration specs; session/cookie handling (the cookie is `httpOnly` and invisible to `document.cookie`), protected UI against a missing/cleared/tampered session, safe rendering of user-controlled input (no XSS), and the absence of tokens or other sensitive data from the page source, client bundle and browser-visible responses as e2e specs. Same standard as `apps/api`'s — see its CLAUDE.md's Testing section.

## Status

Where things stand now. **How it got here — and why — is in [`HISTORY.md`](HISTORY.md)**; per-module architecture and function references are in `docs/modules/`.

- **Auth** — `/register` and `/login` against `apps/api`, on an `httpOnly` session cookie set by Server Actions and read server-side before render. See `docs/modules/module-web-auth.md`.
- **Dashboard** — `/` is auth-gated with no signed-out state: it redirects to `/login` server-side before producing any JSX, and otherwise greets the caller by their stored name (their email when they have none) beside their avatar and lists their meetings split into upcoming and the three most recent past ones, each row linking to its meeting.
- **Profile** — `/profile`, auth-gated the same way, shows the account's email, its avatar, a name form and a password form, both stored through Server Actions; linked from the dashboard beside sign-out. The avatar can be uploaded, replaced and removed there, with the same mark rendered beside the dashboard greeting; its bytes move through a same-origin proxy Route Handler (fields go through Server Actions, which cap their request body at 1 MB), and the image URL carries the last change time so a replaced or removed avatar cannot be repainted from cache. A password change re-writes the session cookie with the token `apps/api` answers with, so the caller stays signed in while every other session of that account is revoked; a wrong current password comes back as a `403` shown on the form in place, while a `401` — the revoked or expired session — sends `/`, `/profile` and `/meetings/[id]` alike to `/login` before render. See `docs/modules/module-web-profile.md`.
- **Meeting page** — `/meetings/[id]` shows a meeting's fields, its live and deleted files, and handles upload (per-file progress, cancel, retry), download, in-page preview (video/audio/image/PDF) and delete/restore. Bytes move through same-origin proxy Route Handlers that attach the session token server-side, so it never reaches the browser. See `docs/modules/module-web-meeting-files.md`.
- **UI** — HeroUI v3 + Tailwind CSS v4, theme fixed to light.

Update this section when the current state changes, and record the change itself in `HISTORY.md`.
