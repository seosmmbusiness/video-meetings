# apps/web/src (auth pages)

Architecture and function reference for the registration and login UI: `/register` and `/login`, plus the session helpers they share with the home page.

This is apps/web's first real feature module. It talks to `apps/api`'s `src/auth` module (see `module-api-auth.md`) over plain `fetch`, using the `POST /auth/register` / `POST /auth/login` contract documented there — there's no shared types package between the two apps, so the DTO shapes are duplicated by hand in `lib/auth-api.ts` and must be kept in sync manually if the backend DTOs change.

## Architecture

- `app/register/page.tsx`, `app/login/page.tsx` — client components (`'use client'`, needed for live per-keystroke validation and controlled inputs) rendering a HeroUI `Card` + `Form`. Both bind their `Form` to a Server Action (`action={formAction}` from `useActionState`) rather than an `onSubmit` handler.
- `app/actions/auth.ts` — `'use server'` Server Actions: `registerAction`/`loginAction` (the two `useActionState` actions backing the forms above — validate the password confirmation, call `lib/auth-api.ts`, store the returned JWT via `lib/session.ts`, and `redirect('/')` on success, or return `{ error }` on failure) and `logoutAction` (bound directly to the home page's sign-out `<form>`; clears the session cookie, no redirect needed).
- `lib/auth-api.ts` — the HTTP client: `registerAccount`/`loginAccount` post to `API_BASE_URL` (root `.env`, default `http://localhost:3001`, apps/api's dev port), parse the JSON response, and throw `ApiError` (with the backend's status code and message) on a non-2xx response. `import 'server-only'` — only ever called from `app/actions/auth.ts`, never the browser, now that auth is server-to-server.
- `lib/session.ts` — the session cookie: `getSession()` (reads the `httpOnly` cookie, for use in Server Components/Actions), `setSessionCookie`/`clearSessionCookie` (used by the Server Actions above), and `getEmailFromToken`/`getExpiryFromToken` (decode the JWT payload's `email`/`exp` claims, display/expiry-only, signature not verified — see Gotchas). `import 'server-only'`.
- `app/page.tsx` (home) — an `async` Server Component. Calls `getSession()` directly (no client read, no `useEffect`/`useSyncExternalStore`) and renders either "Get started"/"Sign in" links or a "Signed in as `<email>`" state + a sign-out form, entirely server-rendered.
- `e2e/auth.spec.ts` — Playwright coverage: register (success, password-mismatch, duplicate-email), login (success, wrong-password), sign-out, and the register↔login cross-links. Runs against a real `apps/api` + Postgres; Playwright's `webServer` only starts `apps/web`, so the API and DB must already be running (`npm run db:up`, `npm run dev:api` or root `npm run dev`).

## Gotchas (non-obvious, worth preserving)

- **Cookie-based session, not `localStorage`.** The JWT lives in an `httpOnly`, first-party `video-meetings.session` cookie set by `apps/web`'s own server (inside `registerAction`/`loginAction`) immediately after a successful call to `apps/api`. This is what lets `app/page.tsx` read sign-in state with `next/headers`' `cookies()` _before_ the page renders — no flash of the signed-out state on load or hard refresh, satisfying `apps/web/CLAUDE.md`'s no-flash rule. The cookie's `secure` flag is `process.env.NODE_ENV === 'production'` (plain HTTP works in local dev), `sameSite: 'lax'`, and its `expires` is set from the JWT's own `exp` claim (via `getExpiryFromToken`) rather than a guessed duration, so the cookie never outlives — or expires before — the token it holds.
- **`API_BASE_URL` comes from the monorepo-root `.env`, not an `apps/web`-local one.** `apps/web` has no `.env` of its own; Next.js only auto-loads `.env*` files from an app's own directory. `next.config.ts` calls `@next/env`'s `loadEnvConfig()` pointed two levels up (mirroring how `apps/api`'s `prisma.config.ts`/`ConfigModule` reach the same root `.env`) before the config — and therefore anything reading `process.env` at runtime — is evaluated. Since `getApiBaseUrl()` is server-only code, this is a plain env var, not `NEXT_PUBLIC_`-prefixed (no browser bundling needed).
- **That `loadEnvConfig()` call must pass `forceReload: true`, or it silently no-ops.** Next.js already calls `loadEnvConfig` once internally, for this app's own (nonexistent) `.env`, before `next.config.ts` ever runs; `@next/env` caches its result at module scope (`combinedEnv`/`p` in its source) and any later call without `forceReload` just returns that cached (empty) result instead of reading a different directory — `API_BASE_URL` would end up `undefined` and `getApiBaseUrl()`'s hardcoded fallback would silently take over, masking the bug (it happens to match the local dev port). Verified by pointing `API_BASE_URL` at a dead port and confirming register/login actually fail — they only do with `forceReload: true` in place.
- **`/auth/register` and `/auth/login` are now called server-to-server**, not from the browser — the Server Actions in `app/actions/auth.ts` run on `apps/web`'s server and `fetch` `apps/api` directly. `apps/api`'s CORS setup (`CORS_ORIGIN`, see `apps/api/CLAUDE.md`) is no longer needed for _these two_ calls specifically, though it's left in place for any future client-side call to `apps/api`.
- **Server Functions are reachable via direct POST, not just through the UI** (per Next's own Server Actions guidance) — `registerAction`/`loginAction` don't need an auth check (they're the public entry points), and `logoutAction` is safe to call unconditionally (clearing an absent cookie is a no-op), so none of the three need an authorization gate. If a future Server Action performs a privileged mutation, it must check `getSession()` itself — a signed-out `<form>` simply not being rendered is not enough.
- **JWT payload decoding uses `Buffer.from(segment, 'base64url')`, not `atob`.** JWT segments are base64**url**-encoded (`-`/`_`); `atob` only understands standard base64 (`+`/`/`) and can throw or silently mis-decode a payload that happens to contain those characters. Both `getEmailFromToken` and `getExpiryFromToken` in `lib/session.ts` share this via an internal `decodeTokenPayload` helper. Still display/expiry-only — the signature is never verified here; `apps/web` trusts the cookie's contents because it set the cookie itself right after a real `apps/api` response, and any actually-protected `apps/api` call re-verifies the JWT signature server-side via `JwtAuthGuard`.
- **Home page's "Get started"/"Sign in" are real `<a>` links, not buttons**, styled with HeroUI's `buttonVariants()` (from `@heroui/styles`) passed as `className` on a `next/link` `<Link>`, e.g. `<NextLink className={buttonVariants()} href="/register">`. This is deliberate, not cosmetic: passing a function prop (e.g. HeroUI `Button`'s `render` prop) from a Server Component to a Client Component throws at runtime ("Functions cannot be passed directly to Client Components..."), since functions can't cross the RSC server/client serialization boundary unless they're Server Actions. `buttonVariants()` sidesteps this entirely — it's evaluated on the server into a plain class string, so only serializable props (`className`, `href`) cross the boundary. Their accessible role is `"link"`, not `"button"` — `e2e/home.spec.ts` and the `Sign out` spec in `e2e/auth.spec.ts` assert `getByRole('link', ...)` for these two, not `getByRole('button', ...)`.
- **Password confirmation is client-only feedback, but the mismatch check itself now lives in `registerAction`.** `RegisterDto` (backend) has no `confirmPassword` field; the register page's local `password`/`confirmPassword` state still drives instant `isInvalid` styling per keystroke, but the actual "do they match" gate that blocks submission runs server-side in `registerAction` (so it still works with JS disabled) rather than in a client `onSubmit` handler.
- **Client-side password validation mirrors, but doesn't replace, the backend's.** The register page re-implements `RegisterDto`'s complexity regex (`PASSWORD_COMPLEXITY_REGEX`) and length bounds for instant `FieldError` feedback; the backend remains the source of truth; if `RegisterDto`'s rules change, update the copy in `app/register/page.tsx` too.
- **Password field placeholders must not be literal bullet characters.** An empty `Input` with `placeholder="••••••••"` is visually indistinguishable from a filled, masked password — use descriptive placeholder text (e.g. "Create a password") instead.
- **Error messages surface backend validation as-is.** `class-validator`'s `ValidationPipe` returns `message` as a string array for 400s and a plain string for 401/409/429s; `lib/auth-api.ts`'s `extractErrorMessage` joins the array case with spaces so either shape renders as one line in the `Alert` (now sourced from the Server Action's returned `state.error` instead of local component state).
- **Click the checkbox's label text in tests, not the input/control.** HeroUI's `Checkbox`'s animated selection indicator (an absolutely-positioned `::before`/SVG) intercepts direct Playwright clicks on the control mid-transition; `e2e/auth.spec.ts`'s `acceptTerms` helper clicks the "I agree to the terms of service" label text instead, which reliably forwards to the underlying input.

## Function reference

- `RegisterPage(): JSX.Element` (`app/register/page.tsx`) — the registration form; binds `Form` to `registerAction` via `useActionState`.
- `LoginPage(): JSX.Element` (`app/login/page.tsx`) — the login form; binds `Form` to `loginAction` via `useActionState`.
- `Home(): Promise<JSX.Element>` (`app/page.tsx`) — landing page; an `async` Server Component that calls `getSession()` and renders the signed-in/signed-out state accordingly.
- `registerAction(prevState: AuthFormState | undefined, formData: FormData): Promise<AuthFormState>` (`app/actions/auth.ts`) — Server Action backing the register form.
- `loginAction(prevState: AuthFormState | undefined, formData: FormData): Promise<AuthFormState>` (`app/actions/auth.ts`) — Server Action backing the login form.
- `logoutAction(): Promise<void>` (`app/actions/auth.ts`) — Server Action backing the home page's sign-out form.
- `registerAccount(input: RegisterInput): Promise<AuthResponse>` (`lib/auth-api.ts`) — `POST /auth/register`.
- `loginAccount(input: LoginInput): Promise<AuthResponse>` (`lib/auth-api.ts`) — `POST /auth/login`.
- `ApiError` (`lib/auth-api.ts`) — `Error` subclass carrying the HTTP `status` alongside the message.
- `getSession(): Promise<Session | null>` (`lib/session.ts`) — reads and decodes the session cookie.
- `setSessionCookie(token: string): Promise<void>` / `clearSessionCookie(): Promise<void>` (`lib/session.ts`) — write/clear the session cookie.
- `getEmailFromToken(token: string): string | null` / `getExpiryFromToken(token: string): Date | null` (`lib/session.ts`) — decode the JWT payload's `email`/`exp` claims without verifying the signature (display/expiry-only).
