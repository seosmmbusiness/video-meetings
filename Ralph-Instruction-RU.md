# Ralph — ходы, бюджет и восстановление

Рабочее руководство по четырём настройкам, которые решают, как далеко успеет уйти автономная сессия
Ralph до того, как её оборвут, что происходит после обрыва и какие значения брать для фичи того или
иного размера.

Русская версия [`Ralph-Instruction.md`](Ralph-Instruction.md) — при расхождении английский файл
считается основным. Оба — спутники [`docs/ralph-loop.md`](docs/ralph-loop.md), где описано, как
запускать и смотреть за петлёй. Здесь речь только про `.claude/ralph.config.json` и слой поверх него.

## Где живут настройки

Два файла, один поверх другого:

| Файл                           | В git?               | Что это                                                                                |
| ------------------------------ | -------------------- | -------------------------------------------------------------------------------------- |
| `.claude/ralph.config.json`    | да                   | Запись о том, что run попросили сделать.                                               |
| `.claude/ralph.overrides.json` | нет (в `.gitignore`) | Временные поправки — то, что пишет дашборд, когда в два часа ночи вы понижаете модель. |

`effectiveConfig()` (`.claude/ralph/lib.js:105`) склеивает их как `{ ...config, ...overrides }`, и
**с этим результатом спавнится каждое звено цепочки**. Override никогда не трогает уже запущенную
сессию — только следующую. Снять ключ: удалить его из файла overrides или выставить в `null`
(`writeOverrides` выбрасывает null-ключи).

## Что такое turn (ход)

Каждое звено Ralph запускает как headless-сессию:
`claude -p "<prompt>" --model <model> --max-turns <N> …` (`.claude/ralph/lib.js:489`).

**Turn — это один ход ассистента**, то есть один ответ модели, что на практике означает один вызов
инструмента:

```
думает → запускает Bash          ← ход 1
думает → правит файл             ← ход 2
думает → гоняет тесты            ← ход 3
…
думает → финальное сообщение     ← последний ход
```

То есть ход — это не «один обмен репликами с человеком». Прочитать файл — ход. Запустить `npm test` —
ход. Сделать коммит — ход. Одна задача по TDD — red-спека, прогон, реализация, прогон, починка,
коммит, label — стоит примерно 60–150 ходов, а если сюита продолжает падать, то и больше.

`--max-turns` — это **жёсткий обрыв, а не подсказка**. Модель не сворачивает работу по мере
приближения к потолку; процесс просто заканчивается посреди дела на ходу N+1. Именно поэтому
`.claude/hooks/stop.js` зарегистрирован не только на `Stop`, но и на `SessionEnd`: сессия, убитая
своим потолком ходов, до чистого завершения не доходит.

Два потолка, выбор в `lib.js:1049` по `stage === 'task' ? maxTurnsPerTask : maxTurnsPerBookend`:

| Ключ                 | Какие звенья закрывает            | Что там происходит                                                                                                                    |
| -------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `maxTurnsPerTask`    | `task` — одна issue из бэклога    | Весь TDD-цикл: red-спека, реализация, три яруса тестов, коммиты, label `ralph:done`.                                                  |
| `maxTurnsPerBookend` | `open`, `close`, `settle`, `done` | Забрать фазу, открыть PR, закрыть issues и milestone, дописать логи и MS-файл, закрыть фичу. Механическая работа, ходов нужно меньше. |

## Что такое бюджет

`maxBudgetUsdPerSession` уходит в CLI как `--max-budget-usd` (`lib.js:505`): потолок стоимости
токенов **одной сессии** — не фазы и не всего run. Считается фактический расход API: вход (включая
контекст, который растёт с каждым ходом) плюс выход плюс thinking-токены, по цене выбранной модели.
Достижение потолка завершает сессию ровно так же, как потолок ходов.

Два потолка ловят разные отказы, и срабатывает тот, кто раньше:

- **`--max-turns`** ловит «модель зациклилась на 200 мелких действиях».
- **`--max-budget-usd`** ловит «модель сделала 40 ходов, но контекст раздулся до 300k токенов, и
  каждый следующий ход стоит доллар».

Каждая законченная сессия пишет в свой `stream-json`-лог строку `result` с полями `total_cost_usd`,
`num_turns` и `is_error`; дашборд читает именно их (`monitor.js:251-254`) — отсюда и стоимость звена,
и сумма по run.

**Потолка на весь run нет.** Его ограничивают только `maxSessionsPerRun` и `maxRunHours`, поэтому
теоретический худший случай — `maxSessionsPerRun × maxBudgetUsdPerSession`. Реальные run укладываются
сильно ниже, но если нужен бюджет на run — следить за суммой в дашборде придётся самому.

`effort` подпирает те же два потолка с другой стороны: больше thinking-токенов — быстрее сгорает
долларовый бюджет и, как правило, меньше потраченных впустую ходов.

## Что происходит, когда сессия упёрлась в лимит

Полностью автоматически, и это стоит знать наизусть:

1. **Сессия умирает** посреди задачи — реализация недописана, тесты красные, коммита может не быть,
   label `ralph:done` на issue не поставлен.
2. **Срабатывает хук**: `SessionEnd` → `.claude/hooks/stop.js` → `lib.advance()`. Он никогда не ждёт
   сессию, которую спавнит, а маркер на сессию делает пару `Stop` / `SessionEnd` идемпотентной — два
   преемника породиться не могут.
3. **Предыдущее звено проверяется** через `verifyPreviousStage()` (`lib.js:1085`). Для `task`
   критерий ровно один — _есть ли на issue label `ralph:done`?_ Если нет:
   `{ ok: false, retry: true, why: 'issue #134 finished without the ralph:done label', key: 'task-134' }`.
4. **Счётчик попыток** `state.attempts['task-134']` растёт на единицу. Пока он `<= taskRetries`,
   пишется событие `retry` и **спавнится новая сессия на ту же задачу**.
5. **Когда попытки кончились** (`attempts > taskRetries`, то есть после третьего провала), `halt()`
   пишет `.claude/ralph.stop` с причиной `… — retry budget (N) exhausted`, и цепочка встаёт. Дальше
   — вручную.

Неочевидная часть retry: **у новой сессии чистый контекст**, она ничего не помнит о предыдущей — но
**рабочее дерево и ветка остались как есть**, вместе с недописанным кодом. То есть retry — это «новая
сессия читает контракт, смотрит на репозиторий и доделывает», а не «продолжает по памяти». Обычно это
работает, потому что промпт задачи детерминирован, а состояние видно в git. Но если сессия оставила
дерево в противоречивом виде, все три попытки упрутся в одну и ту же стену — и это повод для отката,
а не для ретраев.

Остальные стадии проверяются так же: `open` обязана оставить фазу в `in-progress`, `close` — довести
до `in-review`, `settle` — до `completed`. Label `ralph:blocked` — это `retry: false`, немедленный
halt: сессия сама сказала, что не может продолжать.

## Как восстановить остановившийся run

### 1. Понять, где встали

```bash
node .claude/ralph-start.js --status
```

Печатает id run, `active`, фазу N/M, стадию, текущую issue, число сессий, статус каждой фазы и
причину halt из `.claude/ralph.stop`. Ничего не пишет.

### 2. Понять, что оборвало сессию

```bash
ls .claude/ralph-logs/<runId>/
tail -n 40 .claude/ralph-logs/<runId>/task-1-1-i134-*.jsonl | jq -r '.'
```

Найдите последнюю строку `"type":"result"`: `num_turns`, `total_cost_usd`, `is_error` и `subtype`
скажут, был это потолок ходов, бюджет или просто падение. `events.jsonl` в той же директории —
машинный лог всей цепочки (`spawn`, `retry`, `halt`).

### 3. Привести дерево в порядок

Ralph отказывается стартовать на грязном дереве — префлайт гоняет `git status --porcelain` и
сообщает `the working tree is dirty`. Сначала решите судьбу недописанной работы: закоммитить в ветку
фазы или откатить.

### 4. Выбрать способ возврата

**A — просто продолжить.** Для чистого обрыва (работа закоммичена, сюиты зелёные, просто не хватило
ходов на последние шаги):

```bash
node .claude/ralph-start.js --resume
```

`--resume` сохраняет `runId`, `phaseIndex`, `stage` **и `attempts`** (`ralph-start.js:225`), то есть
потраченные попытки остаются потраченными, и снимает halt, удаляя `.claude/ralph.stop`
(`ralph-start.js:233`). Это же команда для «я поднял потолки в overrides, дай задаче ещё заход».

Чтобы начать счёт попыток заново — либо обнулите `attempts` в `.claude/ralph-state.json` руками
перед резюмом, либо стартуйте без `--resume` (тогда сбросятся и `sessions`, и `startedAt` — это уже
новый run).

**B — начать с конкретного места.**

```bash
node .claude/ralph-start.js --resume --phase 1     # с начала указанной фазы
node .claude/ralph-start.js --resume --stage task  # принудительно задать стадию
```

`reconcile()` (`lib.js:734`) всё равно сверяет заявленную стадию с MS-файлом и состоянием PR на
GitHub, и **MS-файл выигрывает любое расхождение** — указать цепочке стадию можно, соврать про уже
сделанное нельзя.

**C — откатить.** Когда сессия оставила мусор. Три режима, все на клавише `r` в дашборде
(`node .claude/ralph-watch.js --ui`):

| Режим                       | Что делает                                                                                                                                                                                   |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Restart the current link    | Убивает сессию, сбрасывает ветку фазы на checkpoint, снятый в момент старта этого звена, и запускает ту же стадию заново. Задача, дошедшая до `ralph:done`, теряет label вместе с коммитами. |
| Undo the last finished task | Откатывает к состоянию до этой задачи, снимает `ralph:done` и отдаёт её цепочке снова. Задача, которую ретраили, откатывается до _первой_ попытки. Дотянуться можно только до фазы в работе. |
| Revert a merged phase PR    | Режет `revert/<slug>-phase-<N>`, делает там реверт merge-коммита, пушит и открывает PR. **В base-ветку ничего не пушится**, run встаёт.                                                      |

Безопасными их делают две вещи: любой откат сначала _планируется_ — argv каждого шага строится как
данные и проверяется в `node --test .claude/ralph/monitor.test.js`, — и всё, что сброс выбросит,
сначала сохраняется в ветку `ralph-backup/<runId>-<timestamp>`. Untracked-файлы не трогаются, если
специально не отметить галочку, и бэкапа для них нет. Невозможный откат не меняет ничего: план
строится до того, как убивают сессию. У run, начатого до появления checkpoints, их нет — и откат
честно об этом скажет, а не станет угадывать.

## Рекомендуемые настройки по размеру фичи

Четыре пресета — от изменения на один вечер до фичи, перекраивающей схему и оба приложения. Размер
меряется тем, что реально лежит в фазе, а не тем, насколько важной кажется фича.

|                          | **Small**                                          | **Medium**                                 | **Large**                             | **Heavy**                                           |
| ------------------------ | -------------------------------------------------- | ------------------------------------------ | ------------------------------------- | --------------------------------------------------- |
| Типичная форма           | 1 фаза, 2–4 задачи, один слой, без изменения схемы | 2–3 фазы, 4–8 задач на фазу, одна миграция | 4–6 фаз, оба слоя, несколько миграций | 6+ фаз, сквозной рефакторинг, новая внешняя граница |
| `model`                  | `sonnet`                                           | `opus`                                     | `opus`                                | `opus`                                              |
| `fallbackModel`          | `sonnet`                                           | `sonnet`                                   | `sonnet`                              | `sonnet`                                            |
| `effort`                 | `low`                                              | `medium`                                   | `medium`                              | `high`                                              |
| `maxTurnsPerTask`        | `80`                                               | `150`                                      | `200`                                 | `300`                                               |
| `maxTurnsPerBookend`     | `60`                                               | `100`                                      | `120`                                 | `150`                                               |
| `maxBudgetUsdPerSession` | `8`                                                | `20`                                       | `45`                                  | `80`                                                |
| `taskRetries`            | `1`                                                | `2`                                        | `2`                                   | `2`                                                 |
| `maxSessionsPerRun`      | `15`                                               | `35`                                       | `60`                                  | `100`                                               |
| `maxRunHours`            | `2`                                                | `5`                                        | `8`                                   | `12`                                                |
| Худший случай по run     | ~$120                                              | ~$700                                      | ~$2700                                | ~$8000                                              |

Последняя строка — это `maxSessionsPerRun × maxBudgetUsdPerSession`, то есть сколько потолки
_разрешают_, а не сколько ожидать. Реальные run выходят сильно дешевле, потому что большинство
звеньев не добирает свой бюджет; считайте это радиусом поражения ночной петли, которая пошла не так.

Готовым JSON, под копипаст в `.claude/ralph.overrides.json`:

```jsonc
// Small — одна фаза, без изменения схемы
{ "model": "sonnet", "fallbackModel": "sonnet", "effort": "low",
  "maxTurnsPerTask": 80, "maxTurnsPerBookend": 60,
  "maxBudgetUsdPerSession": 8, "taskRetries": 1 }

// Medium — пара фаз, одна миграция
{ "model": "opus", "fallbackModel": "sonnet", "effort": "medium",
  "maxTurnsPerTask": 150, "maxTurnsPerBookend": 100,
  "maxBudgetUsdPerSession": 20, "taskRetries": 2 }

// Large — оба приложения, несколько фаз
{ "model": "opus", "fallbackModel": "sonnet", "effort": "medium",
  "maxTurnsPerTask": 200, "maxTurnsPerBookend": 120,
  "maxBudgetUsdPerSession": 45, "taskRetries": 2 }

// Heavy — сквозная работа, новая граница
{ "model": "opus", "fallbackModel": "sonnet", "effort": "high",
  "maxTurnsPerTask": 300, "maxTurnsPerBookend": 150,
  "maxBudgetUsdPerSession": 80, "taskRetries": 2 }
```

`maxSessionsPerRun` и `maxRunHours` лучше держать в committed-конфиге, а не в overrides — они
описывают форму фичи, а не поправку, сделанную посреди run.

### Как читать пресеты

- **`model` / `fallbackModel`.** Fallback — это то, на что переключится CLI, когда основная модель
  недоступна или перегружена; без него сессия просто умрёт и сожжёт попытку. Держать везде `sonnet`
  как fallback — в этом и смысл: деградировавшая сессия лучше остановившегося run.
- **`effort`.** В committed-конфиге его нет, поэтому override его _добавляет_ — сессии получают флаг,
  которого у них не было. `low` на механической работе, `high` только там, где решения настоящие.
- **Потолки ходов.** Поднимать `maxTurnsPerTask` выше ~250 обычно неверное решение. Сессия на 300
  ходов тащит огромный контекст, каждый ход дороже предыдущего, и вы упрётесь в долларовый потолок
  раньше, чем в потолок ходов. Симптом «дробить задачу, а не поднимать потолок» виден в логе: большой
  `num_turns` вместе с циклом «правка → тест → та же ошибка».
- **`taskRetries`.** При `2` — три попытки всего. Больше почти не помогает: если два ретрая с чистым
  контекстом не справились, дело в дереве или в самой задаче, а не в числе попыток. Halt и откат.

### Калибровка по реальному run

После первой фазы вытащите числа из логов, а не гадайте:

```bash
grep -h '"type":"result"' .claude/ralph-logs/<runId>/*.jsonl \
  | jq -r '[.num_turns, .total_cost_usd, .is_error] | @tsv'
```

- Сессии кучкуются у потолка ходов → задачи слишком большие, дробите их в плане.
- Сессии кучкуются у долларового потолка при _малом_ числе ходов → раздут контекст; посмотрите, что
  тянет в себя промпт, или понизьте `effort`.
- Сессии заканчиваются на доле от обоих потолков → потолки работают чистой страховкой, и более
  дешёвый пресет сделал бы ту же работу.
