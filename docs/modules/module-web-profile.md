# apps/web/src (profile page + the dashboard greeting)

Architecture and function reference for `/profile` — the page showing the signed-in account's email, name and avatar, the form that changes the name, and the control that uploads, replaces and removes the avatar — plus the avatar mark and name-or-email greeting the dashboard renders from the same data.

It talks to `apps/api`'s `src/profile` module (see `module-api-profile.md`) over `GET /profile` / `PATCH /profile` for the fields and `GET` / `POST` / `DELETE /profile/avatar` for the bytes, and shares the session cookie, `ApiError`, `getApiBaseUrl()` and `proxyToApi` with the auth and meeting-files modules (see `module-web-auth.md`, `module-web-meeting-files.md`). There is no shared types package between the two apps, so `Profile` in `lib/profile-api.ts` is a hand-copy of the backend's `ProfileResponseDto`, and `lib/avatar-limits.ts` is a hand-copy of the backend's avatar limits and refusal wording — both have to be kept in sync manually when the backend changes.

**Fields and bytes take different paths on purpose (D-12).** The name goes through a Server Action; the avatar goes through a same-origin proxy Route Handler, because Next caps a Server Action's request body at 1 MB by default against a 5 MB avatar, and raising `serverActions.bodySizeLimit` would raise the ceiling for every action in the app.

## Architecture

- `lib/profile-api.ts` — the HTTP client, `import 'server-only'`. `getProfile(token)` / `updateProfileName(token, name)` call `GET` / `PATCH /profile` against `API_BASE_URL` with the caller's bearer token and `cache: 'no-store'`, sharing one internal `requestProfile` helper, and throw `ApiError` on a non-2xx exactly as `meetings-api.ts` does — the upstream status is preserved, so a `401` (session gone) stays distinguishable from a `403` (refused, stay put) for phase 6's password form (D-11). Re-exports `ApiError` from `auth-api.ts` rather than declaring a second one. Also holds `displayName(name, email)`, the pure name-or-email choice both `/` and the profile page render.
- `app/profile/page.tsx` — an `async` Server Component with no signed-out state, the shape `/` already uses: `getSession()` first, `redirect('/login')` before any JSX both when there is no cookie and when `apps/api` answers `401` for the one there is (AC-14). Email, name and the avatar all come out of the first server response, with no client-side read after mount (AC-1). A non-`401` failure renders a danger `Alert` in place of the profile rather than crashing the page. Footer links back to the dashboard.
- `app/api/profile/avatar/route.ts` — the same-origin byte proxy, exporting `GET`, `POST` and `DELETE`. Each one calls `getSession()` first and answers `401` with no body **before any upstream call**, then hands off to `proxyToApi(request, session.token, '/profile/avatar')` — the shared allow-listed forwarder both meeting-file proxies use (see `module-web-meeting-files.md`), which attaches the bearer token server-side and drops the caller's own `Authorization`. The upstream path is a module constant with no caller-controlled segment at all, so nothing the browser appends to the route's URL can steer it (AC-17, D-12). `GET` is what the rendered `<img>` fetches, so the session token is never needed in the browser to see one's own avatar (D-8).
- `components/profile/avatar-uploader.tsx` — `'use client'`. The upload/replace/remove control on `/profile`: a visually hidden file input driven by a HeroUI `Button`, `POST`ing the chosen file to the proxy as the `avatar` part `FileInterceptor('avatar')` expects, and — when the account already holds one — a second button issuing `DELETE` through the same route (AC-9). Both call `router.refresh()` on success, which is what re-renders the server tree with the new `avatarUpdatedAt` and so changes the image URL (AC-6). `refuseAvatar` runs first as a convenience filter; anything it lets through that `apps/api` still refuses comes back and is shown **verbatim** via `refusalFrom`, inside a `role="alert"` wrapper (AC-7, AC-8). A success is said in words too, in a separate `role="status"` line — the only other sign of one is the image itself, which is never announced — and the hidden input carries `tabIndex={-1}`, since `sr-only` hides it without removing its focusability and it would otherwise be an invisible tab stop beside the button that opens it.
- `lib/avatar-limits.ts` — the browser-side avatar rules, hand-duplicated from `apps/api`'s `profile.constants.ts`: `MAX_AVATAR_BYTES` (`5_242_880`), `ACCEPTED_AVATAR_MIME_TYPES` (`image/png`, `image/jpeg`, `image/webp`), the `accept` attribute built from them, and the two refusal strings copied word for word from the API's `413`/`415` bodies so the page reads identically whichever side caught the file. Same role — and same hand-duplication caveat — as `file-limits.ts`.
- `components/profile/user-avatar.tsx` — `'use client'`. HeroUI `Avatar` at a fixed rendered size: `Avatar.Image` over the proxy URL when `hasAvatar`, `Avatar.Fallback` over the initials of the name's first two words (or the email's first letter) when not (D-13). Both branches are decided from props the server already resolved, so the mark is in the first server response rather than filled in after mount (AC-1, AC-5). `src` is `/api/profile/avatar?v=<avatarUpdatedAt epoch ms>`; `next/image` is deliberately not used (D-13, gotcha below).
- `components/profile/name-form.tsx` — `'use client'`. The name field and Save button, bound to `updateNameAction` through `useActionState` (D-12: fields go through Server Actions, only bytes need a Route Handler). Shows the API's refusal on the field itself via HeroUI's `FieldError` inside a `role="alert"` wrapper (the refusal lands while focus is on Save, where `aria-describedby` alone would never be read), keeps what was typed through a refusal, and announces a successful save through an `aria-live` status region.
- `app/actions/profile.ts` — `'use server'`. `updateNameAction`, backing the form above: `getSession()` is its **first statement** and the signed-out outcome is returned without touching `apps/api` (S-3, AC-19), exactly as `actions/files.ts` guards. On success it `revalidatePath`s `/profile` and `/` (both are server-rendered and both show the name) and returns only `{ ok, name }` — never the upstream body or the token, since an action's return value is serialised into the page payload (D-12, S-6).
- `app/page.tsx` (dashboard) — renders the same `UserAvatar` beside the greeting, from the same server-side profile, so the avatar is in the first response here too (AC-5); when the profile call failed it falls back to the session's email and an initials mark rather than dropping the element, so the layout is the same either way. Greets by `displayName(profile.name, profile.email)` in the server-rendered HTML (AC-5) — the fallback email comes from the profile rather than the session, whose own `email` is a decoded claim typed `string | null`, fetches the profile and the meetings together with `Promise.allSettled` (both need only the session token, so neither waits on the other), redirects to `/login` if **either** call answers `401`, and adds the "Profile" link beside sign-out. The rest of the dashboard is the auth module's (see `module-web-auth.md`).

Tests, per tier:

- `lib/profile-api.spec.ts` — the client's request shape (bearer token, `no-store`, `PATCH` body), `ApiError` status preservation incl. `401` vs `403`, `class-validator`'s array-of-messages joined into one refusal, and `displayName`'s fallbacks.
- `components/profile/user-avatar.spec.tsx`, `name-form.spec.tsx`, `avatar-uploader.spec.tsx` — RTL: initials and their fallbacks, a name of markup rendering as text (AC-16), submitting/clearing/correcting a name, the refusal shown verbatim and the typed value surviving it (AC-3), the save confirmation; for the avatar, the `?v=` source built from `avatarUpdatedAt` and the mark returning to initials after a removal, plus the uploader's browser-side size and declared-type refusals, the API's own refusal surfaced word for word, and `router.refresh()` after a successful upload or removal.
- `app/actions/profile.int-spec.ts` — the action called directly with `next/headers` mocked: no session → no upstream `fetch` at all (S-3, AC-19), the bearer token attached server-side, an empty name sent through as a value (AC-4), the refusal returned verbatim (AC-3), and nothing of the upstream body or the token in the returned state (D-12).
- `app/api/profile/avatar/route.int-spec.ts` — the three handlers called directly, the tier `apps/web/CLAUDE.md` reserves for the proxy's security-critical seams: the `401` answered before any upstream `fetch` happens at all, the bearer token attached server-side while a caller-supplied `Authorization` is dropped, the request/response header allow-list, and the fixed upstream path holding whatever the caller puts in the route's own URL.
- `e2e/profile.spec.ts` — Playwright: the auth gate (no cookie, tampered cookie, well-formed-but-unsigned cookie) with no profile data in the body, the first-response render of email/name/avatar, the dashboard link, trimming, the over-80 refusal, clearing, markup-as-text on both pages, and the absence of the session token from the page HTML and the client bundle (AC-17). Its avatar half drives the real upload path: the image appearing on `/profile` and on `/` with no manual reload (AC-6), a replacement being served instead of what it replaced (AC-6), the over-5 MB and the renamed-non-image refusals shown on screen while the stored avatar stays untouched (AC-7, AC-8), removal returning both pages to the placeholder (AC-9), and no token on the avatar path in any browser-visible request or response (AC-17). `e2e/home.spec.ts` covers the dashboard greeting (AC-5). Both need a real `apps/api` + Postgres already running — Playwright only starts `apps/web`.

## Gotchas (non-obvious, worth preserving)

- **The name field is controlled on purpose.** React 19 resets an _uncontrolled_ field once a form action settles, which would throw away what was typed every time `apps/api` refused it. `NameForm` holds the value in state so a refusal costs no retyping (AC-3); the price is having to sync back to the stored value after a successful save, which it does by setting state during render (React's own answer to deriving state from props) when the action returns a name it hasn't shown yet.
- **The refusal is withdrawn as soon as the field is edited.** It's about the value that was submitted, so `NameForm` compares the current value against the submitted one and drops `state.error` once they differ. Without that the field stays `isInvalid`, the browser's own constraint check blocks every further submission, and the form is stuck on the refusal it just showed — a corrected name could never be saved.
- **An empty name is a value, not an omission.** `''` is how a stored name is cleared (AC-4), so nothing on the path — the form, the action, or `updateProfileName` — treats it as "no change" or skips the call. `displayName` then falls back to the email; it also treats an all-whitespace name as no name, since `apps/api` returns `null` for a cleared one but a blank greeting would be the same bug either way.
- **The client-side hint mirrors `apps/api`'s rules, it does not enforce them.** The field carries no `maxLength`, so an over-long name reaches the API and comes back with the API's own wording instead of being silently truncated in the browser. The "Up to 80 characters" description is a copy of the backend rule and has to be updated with it — same hand-duplication caveat as `file-limits.ts`.
- **A Server Action is reachable by direct POST, not only through the rendered form.** `updateNameAction` checks `getSession()` as its first statement and returns the signed-out outcome without calling `apps/api` (S-3). The form not being rendered to a signed-out visitor is not a boundary, and `apps/api`'s own refusal would arrive one boundary too late — as an unhandled error rather than a stated outcome.
- **An action's return value is published to the browser.** It is serialised into the page payload, so `UpdateNameState` carries `{ ok, name?, error? }` and never the upstream response object or anything derived from the session token (D-12, S-6). This matters more in phase 6, where the password route answers with a fresh `accessToken`.
- **A profile that fails to load doesn't put a banner on the dashboard.** `/` falls back to greeting by the email — which is what it falls back to anyway when no name is set — while `/profile` is where a broken `/profile` is actually reported. Only a `401` from either call is escalated, and it redirects to `/login`.
- **`redirect()` works by throwing, so it must never be called inside a `try` that swallows what it throws.** The profile page calls it from the `catch` handling the `401`, not from the `try` around `getProfile` — and it does so before any JSX exists, so nothing of the profile leaks with the redirect (AC-14). The dashboard, for the same reason, does its `401` check after `Promise.allSettled` has already resolved rather than inside a `try`.
- **`next/image` is not an option for the avatar (D-13).** It routes the source through `/_next/image`, which fetches server-side _without_ the browser's cookies — the same-origin proxy would answer `401` and no image would ever render, and the optimizer would write derivatives of a private image into the build cache. HeroUI's `Avatar` (a plain `<img>` plus `Avatar.Fallback`) is used instead.
- **Avatar size is fixed so the image costs no layout shift.** The fallback initials render at the same `size="lg"` the image does, so which branch renders changes nothing about the box.
- **`?v=<avatarUpdatedAt>` is what makes a replaced avatar stop showing, not the cache headers.** The API sends `Cache-Control: private, max-age=60` — T-1's 60-second private window, not `no-store` (D-8) — but the browser's own copy of a URL it already painted is the thing AC-6 and AC-9 are actually about, so the URL itself has to change. `avatarSrc` puts the account's last avatar change into the query string as epoch ms; a missing or unparsable timestamp degrades to `v=0` rather than producing no URL, since an avatar that never loads is worse than one cached a little too long. Nothing about the query string reaches the upstream path — the proxy's `/profile/avatar` is a constant (AC-17).
- **`router.refresh()` is the whole refresh mechanism, and it is not optional.** Both pages read `hasAvatar` and `avatarUpdatedAt` server-side, so without the refresh a successful upload changes nothing on screen until a manual reload — and `revalidatePath`, the name form's answer, isn't available here because the upload goes through a Route Handler rather than a Server Action.
- **What the server decides is the _branch_, not the `<img>` itself.** `hasAvatar` and `avatarUpdatedAt` are resolved server-side, so which mark renders is settled in the first response (AC-1, AC-5) — but HeroUI's `Avatar.Image` only emits the `<img>` once a client-side `Image()` reports the source loaded, so the served HTML never contains it and the initials are what a JS-less browser keeps. That is the image loading, not a state flip (T-2); don't go looking for the `<img>` in `page.content()`.
- **`UserAvatar` needs `role="img"` for its `aria-label` to exist at all.** The root renders as a plain `<span>`, where a label on a generic role is dropped, and `Avatar.Image`'s `alt` is deliberately empty — so without the role the mark has no accessible name in either branch. RTL's `getByLabelText` reads the attribute directly and cannot catch this.
- **`UserAvatar` is keyed on its source.** HeroUI's `Avatar` remembers that an image loaded and keeps its fallback hidden afterwards, so removing an avatar under a mounted mark would leave an empty circle instead of the initials (AC-9). Keying on `src ?? 'fallback'` makes each state a fresh mark with nothing remembered. `Avatar.Image`'s `alt` is empty on purpose — the mark's own `aria-label` carries the accessible name, and describing the image again would announce it twice.
- **The file input's value is cleared on every change.** Choosing the same file twice fires no `change` event, so after a refusal a user who picked the same file again would see nothing happen at all — clearing `event.target.value` immediately makes the identical pick a new event.
- **The browser-side checks are a convenience, not the boundary.** `refuseAvatar` reads only `file.type` and `file.size`, both of which the file declares about itself; only `apps/api` reads the bytes (3.4). So the messages in `avatar-limits.ts` are copied verbatim from the API's `413`/`415` bodies — the page must read the same whichever side caught it — and anything the filter lets through is refused upstream and surfaced word for word rather than reworded.
- **The upload refusal needs its own live region.** It lands while focus is still on the upload button, and HeroUI's `Alert` carries no role of its own, so the `role="alert"` wrapper is what a screen reader user hears at all — the same reason `NameForm` wraps its `FieldError`.
- **The proxy's `401` is a real boundary, not a convenience.** A Route Handler is reachable by direct request like a Server Action is, so `getSession()` is the first statement in each of `GET`/`POST`/`DELETE` and the `401` is answered with no body before any upstream call — otherwise an unauthenticated `POST` would stream 5 MB to `apps/api` just to be refused there.
- **The dashboard's avatar row is its own element inside `Card.Content`, not the slot itself.** Putting the flex classes on `Card.Content` left the mark stacked above the greeting instead of beside it — the slot brings layout of its own — which only showed up in the browser, since nothing about the markup reads wrong. Same shape as the profile page's own avatar row.
- **The dashboard's two fetches run together, not in sequence.** `Promise.allSettled` over `getProfile` and `listMeetings` — both need only the session token — so the greeting costs no extra round trip on the critical path. It also means the `401` check has to look at _both_ results before deciding, rather than at whichever one is awaited first.

## Function reference

- `getProfile(token: string): Promise<Profile>` (`lib/profile-api.ts`) — `GET /profile`, bearer-authenticated, `no-store`. Throws `ApiError` (`401` session gone, `403` refused).
- `updateProfileName(token: string, name: string): Promise<Profile>` (`lib/profile-api.ts`) — `PATCH /profile` with `{ name }`; `''` clears the stored name. Throws `ApiError` (`400` carries the API's refusal).
- `displayName(name: string | null, email: string): string` (`lib/profile-api.ts`) — the stored name when there is one, the email otherwise (blank and whitespace-only count as none).
- `Profile` (`lib/profile-api.ts`) — hand-copy of `apps/api`'s `ProfileResponseDto`: `id`, `email`, `name`, `hasAvatar`, `avatarUpdatedAt` (the API's `Date` arrives as its JSON string form).
- `ProfilePage(): Promise<JSX.Element>` (`app/profile/page.tsx`) — the auth-gated profile page; `getSession()`, `redirect('/login')` on no session or a `401`, then email + `UserAvatar` + `NameForm`.
- `UserAvatar({ name, email, hasAvatar?, avatarUpdatedAt?, label? }): JSX.Element` (`components/profile/user-avatar.tsx`) — the avatar mark: the stored image when `hasAvatar`, the initials otherwise. `label` defaults to "Your avatar" so the same mark can be reused elsewhere; `hasAvatar` and `avatarUpdatedAt` default to `false`/`null`, which is the initials.
- `initialsFor(name: string | null, email: string): string` (`components/profile/user-avatar.tsx`, module-private) — one or two upper-cased characters: the first letters of the name's first two words, or the email's first letter.
- `avatarSrc(avatarUpdatedAt: string | null): string` (`components/profile/user-avatar.tsx`, module-private) — `/api/profile/avatar?v=<epoch ms>`, falling back to `v=0` on a missing or unparsable timestamp.
- `AvatarUploader({ hasAvatar }): JSX.Element` (`components/profile/avatar-uploader.tsx`) — the upload/replace control, plus the removal control when `hasAvatar`; refreshes the server tree on success and shows the refusal otherwise.
- `refusalFrom(response: Response, fallback: string): Promise<string>` (`components/profile/avatar-uploader.tsx`, module-private) — reads `apps/api`'s own `message` (string or `class-validator` array) out of a proxied response; falls back to `<fallback> (<status>).`
- `refuseAvatar(file: File): string | null` (`lib/avatar-limits.ts`) — the browser-side declared-type-then-size check; the refusal to show, or `null` to send.
- `MAX_AVATAR_BYTES`, `ACCEPTED_AVATAR_MIME_TYPES`, `AVATAR_ACCEPT_ATTRIBUTE`, `AVATAR_SIZE_LIMIT_MESSAGE`, `UNSUPPORTED_AVATAR_TYPE_MESSAGE` (`lib/avatar-limits.ts`) — the hand-copied limits, the input's `accept` list, and the two refusal strings matching the API's `413`/`415` bodies verbatim.
- `GET(request: Request): Promise<Response>` (`app/api/profile/avatar/route.ts`) — serves the caller's own avatar bytes through the proxy; `401` with no body when signed out.
- `POST(request: Request): Promise<Response>` (`app/api/profile/avatar/route.ts`) — uploads or replaces the avatar, streaming the multipart body onward and returning the API's refusal unchanged; `401` with no body when signed out.
- `DELETE(request: Request): Promise<Response>` (`app/api/profile/avatar/route.ts`) — removes the stored avatar; `401` with no body when signed out.
- `NameForm({ name }): JSX.Element` (`components/profile/name-form.tsx`) — the name field and Save button, bound to `updateNameAction` via `useActionState`.
- `updateNameAction(prevState: UpdateNameState | undefined, formData: FormData): Promise<UpdateNameState>` (`app/actions/profile.ts`) — Server Action storing the name; gates on `getSession()` first, revalidates `/profile` and `/`.
- `UpdateNameState` (`app/actions/profile.ts`) — `{ ok: boolean; name?: string; error?: string }`, the only thing the action returns to the browser.
