# apps/web/src (profile page + the dashboard greeting)

Architecture and function reference for `/profile` — the page showing the signed-in account's email, name and avatar mark, and the form that changes the name — plus the name-or-email greeting the dashboard renders from the same data.

It talks to `apps/api`'s `src/profile` module (see `module-api-profile.md`) over `GET /profile` / `PATCH /profile`, and shares the session cookie, `ApiError` and `getApiBaseUrl()` with the auth module (see `module-web-auth.md`). There is no shared types package between the two apps, so `Profile` in `lib/profile-api.ts` is a hand-copy of the backend's `ProfileResponseDto` and has to be kept in sync manually if that DTO changes.

Avatar **images** are phase 4's work and are not here yet: until then the mark is always initials.

## Architecture

- `lib/profile-api.ts` — the HTTP client, `import 'server-only'`. `getProfile(token)` / `updateProfileName(token, name)` call `GET` / `PATCH /profile` against `API_BASE_URL` with the caller's bearer token and `cache: 'no-store'`, sharing one internal `requestProfile` helper, and throw `ApiError` on a non-2xx exactly as `meetings-api.ts` does — the upstream status is preserved, so a `401` (session gone) stays distinguishable from a `403` (refused, stay put) for phase 6's password form (D-11). Re-exports `ApiError` from `auth-api.ts` rather than declaring a second one. Also holds `displayName(name, email)`, the pure name-or-email choice both `/` and the profile page render.
- `app/profile/page.tsx` — an `async` Server Component with no signed-out state, the shape `/` already uses: `getSession()` first, `redirect('/login')` before any JSX both when there is no cookie and when `apps/api` answers `401` for the one there is (AC-14). Email, name and the avatar mark all come out of the first server response, with no client-side read after mount (AC-1). A non-`401` failure renders a danger `Alert` in place of the profile rather than crashing the page. Footer links back to the dashboard.
- `components/profile/user-avatar.tsx` — `'use client'`. HeroUI `Avatar` at a fixed rendered size, currently always `Avatar.Fallback` over the initials of the name's first two words, or the email's first letter when no name is set (D-13). Fixed size so nothing shifts once phase 4 puts a real image behind it.
- `components/profile/name-form.tsx` — `'use client'`. The name field and Save button, bound to `updateNameAction` through `useActionState` (D-12: fields go through Server Actions, only bytes need a Route Handler). Shows the API's refusal on the field itself via HeroUI's `FieldError`, keeps what was typed through a refusal, and announces a successful save through an `aria-live` status region.
- `app/actions/profile.ts` — `'use server'`. `updateNameAction`, backing the form above: `getSession()` is its **first statement** and the signed-out outcome is returned without touching `apps/api` (S-3, AC-19), exactly as `actions/files.ts` guards. On success it `revalidatePath`s `/profile` and `/` (both are server-rendered and both show the name) and returns only `{ ok, name }` — never the upstream body or the token, since an action's return value is serialised into the page payload (D-12, S-6).
- `app/page.tsx` (dashboard) — greets by `displayName(profile.name, session.email)` in the server-rendered HTML (AC-5), fetches the profile and the meetings together with `Promise.allSettled` (both need only the session token, so neither waits on the other), redirects to `/login` if **either** call answers `401`, and adds the "Profile" link beside sign-out. The rest of the dashboard is the auth module's (see `module-web-auth.md`).

Tests, per tier:

- `lib/profile-api.spec.ts` — the client's request shape (bearer token, `no-store`, `PATCH` body), `ApiError` status preservation incl. `401` vs `403`, `class-validator`'s array-of-messages joined into one refusal, and `displayName`'s fallbacks.
- `components/profile/user-avatar.spec.tsx`, `name-form.spec.tsx` — RTL: initials and their fallbacks, a name of markup rendering as text (AC-16), submitting/clearing/correcting a name, the refusal shown verbatim and the typed value surviving it (AC-3), the save confirmation.
- `app/actions/profile.int-spec.ts` — the action called directly with `next/headers` mocked: no session → no upstream `fetch` at all (S-3, AC-19), the bearer token attached server-side, an empty name sent through as a value (AC-4), the refusal returned verbatim (AC-3), and nothing of the upstream body or the token in the returned state (D-12).
- `e2e/profile.spec.ts` — Playwright: the auth gate (no cookie, tampered cookie, well-formed-but-unsigned cookie) with no profile data in the body, the first-response render of email/name/avatar, the dashboard link, trimming, the over-80 refusal, clearing, markup-as-text on both pages, and the absence of the session token from the page HTML and the client bundle (AC-17). `e2e/home.spec.ts` covers the dashboard greeting (AC-5). Both need a real `apps/api` + Postgres already running — Playwright only starts `apps/web`.

## Gotchas (non-obvious, worth preserving)

- **The name field is controlled on purpose.** React 19 resets an _uncontrolled_ field once a form action settles, which would throw away what was typed every time `apps/api` refused it. `NameForm` holds the value in state so a refusal costs no retyping (AC-3); the price is having to sync back to the stored value after a successful save, which it does by setting state during render (React's own answer to deriving state from props) when the action returns a name it hasn't shown yet.
- **The refusal is withdrawn as soon as the field is edited.** It's about the value that was submitted, so `NameForm` compares the current value against the submitted one and drops `state.error` once they differ. Without that the field stays `isInvalid`, the browser's own constraint check blocks every further submission, and the form is stuck on the refusal it just showed — a corrected name could never be saved.
- **An empty name is a value, not an omission.** `''` is how a stored name is cleared (AC-4), so nothing on the path — the form, the action, or `updateProfileName` — treats it as "no change" or skips the call. `displayName` then falls back to the email; it also treats an all-whitespace name as no name, since `apps/api` returns `null` for a cleared one but a blank greeting would be the same bug either way.
- **The client-side hint mirrors `apps/api`'s rules, it does not enforce them.** The field carries no `maxLength`, so an over-long name reaches the API and comes back with the API's own wording instead of being silently truncated in the browser. The "Up to 80 characters" description is a copy of the backend rule and has to be updated with it — same hand-duplication caveat as `file-limits.ts`.
- **A Server Action is reachable by direct POST, not only through the rendered form.** `updateNameAction` checks `getSession()` as its first statement and returns the signed-out outcome without calling `apps/api` (S-3). The form not being rendered to a signed-out visitor is not a boundary, and `apps/api`'s own refusal would arrive one boundary too late — as an unhandled error rather than a stated outcome.
- **An action's return value is published to the browser.** It is serialised into the page payload, so `UpdateNameState` carries `{ ok, name?, error? }` and never the upstream response object or anything derived from the session token (D-12, S-6). This matters more in phase 6, where the password route answers with a fresh `accessToken`.
- **A profile that fails to load doesn't put a banner on the dashboard.** `/` falls back to greeting by the email — which is what it falls back to anyway when no name is set — while `/profile` is where a broken `/profile` is actually reported. Only a `401` from either call is escalated, and it redirects to `/login`.
- **`redirect()` works by throwing, so it must never be called inside a `try` that swallows what it throws.** The profile page calls it from the `catch` handling the `401`, not from the `try` around `getProfile` — and it does so before any JSX exists, so nothing of the profile leaks with the redirect (AC-14). The dashboard, for the same reason, does its `401` check after `Promise.allSettled` has already resolved rather than inside a `try`.
- **`next/image` is not an option for the avatar (D-13).** It routes the source through `/_next/image`, which fetches server-side _without_ the browser's cookies — the same-origin proxy phase 4 will add would answer `401` and no image would ever render, and the optimizer would write derivatives of a private image into the build cache. HeroUI's `Avatar` (a plain `<img>` plus `Avatar.Fallback`) is used instead.
- **Avatar size is fixed now so phase 4 costs no layout shift.** The fallback initials render at the same `size="lg"` the image will, so swapping in `Avatar.Image` later changes nothing about the box.
- **The dashboard's two fetches run together, not in sequence.** `Promise.allSettled` over `getProfile` and `listMeetings` — both need only the session token — so the greeting costs no extra round trip on the critical path. It also means the `401` check has to look at _both_ results before deciding, rather than at whichever one is awaited first.

## Function reference

- `getProfile(token: string): Promise<Profile>` (`lib/profile-api.ts`) — `GET /profile`, bearer-authenticated, `no-store`. Throws `ApiError` (`401` session gone, `403` refused).
- `updateProfileName(token: string, name: string): Promise<Profile>` (`lib/profile-api.ts`) — `PATCH /profile` with `{ name }`; `''` clears the stored name. Throws `ApiError` (`400` carries the API's refusal).
- `displayName(name: string | null, email: string): string` (`lib/profile-api.ts`) — the stored name when there is one, the email otherwise (blank and whitespace-only count as none).
- `Profile` (`lib/profile-api.ts`) — hand-copy of `apps/api`'s `ProfileResponseDto`: `id`, `email`, `name`, `hasAvatar`, `avatarUpdatedAt` (the API's `Date` arrives as its JSON string form).
- `ProfilePage(): Promise<JSX.Element>` (`app/profile/page.tsx`) — the auth-gated profile page; `getSession()`, `redirect('/login')` on no session or a `401`, then email + `UserAvatar` + `NameForm`.
- `UserAvatar({ name, email, label? }): JSX.Element` (`components/profile/user-avatar.tsx`) — the avatar mark; `label` defaults to "Your avatar" so the same mark can be reused elsewhere.
- `NameForm({ name }): JSX.Element` (`components/profile/name-form.tsx`) — the name field and Save button, bound to `updateNameAction` via `useActionState`.
- `updateNameAction(prevState: UpdateNameState | undefined, formData: FormData): Promise<UpdateNameState>` (`app/actions/profile.ts`) — Server Action storing the name; gates on `getSession()` first, revalidates `/profile` and `/`.
- `UpdateNameState` (`app/actions/profile.ts`) — `{ ok: boolean; name?: string; error?: string }`, the only thing the action returns to the browser.
